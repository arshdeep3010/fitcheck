How it works

It can't claim
what it can't cite.

FitCheck reads a job description, searches the candidate's real repositories, and rates every requirement. A model gives an opinion. Plain code decides what gets claimed, and every "Met" links to the exact lines on GitHub.

01

Six steps, one graph

Each check runs as a LangGraph state graph. The page you used streams each step live as it finishes. Steps with a bright border are plain Python, with no model involved.

  1. parse_jd

    Read the job description

    A chat model lists each requirement. Lists are split ("Spring Security, OAuth2 and JWT" becomes 3 rows), and years, degrees and location are marked as not checkable from code.

    Runs on a chat model
  2. retrieve

    Search the code

    Each requirement becomes a vector and is matched against every indexed code snippet. The closest 5 snippets, plus up to 3 more that keyword search finds by exact name (like from langgraph.graph import StateGraph for "LangGraph"), become that requirement's only possible evidence.

    Runs on embeddings + a vector index
  3. score

    Judge each requirement

    One model call judges all requirements at once: met, partly met or not met, a confidence, and which retrieved snippet is the proof. It can only point at snippets it was shown.

    Runs on a fit scorer
  4. ground

    Apply the grounding rules

    Code checks the model's answer. No valid citation or low confidence means Unverified, whatever the model said. See the rules below.

    Runs on Python rules
  5. check_cv

    Check the CV for the rest

    Only for what code didn't prove: does the CV at least state it? A hit is shown as "Stated on CV", never as Met.

    Runs on CV sections + the same scorer
  6. report

    Write the report

    Scores and the summary are computed in code, not written by a model, so the same verdicts always give the same numbers.

    Runs on Python

If the job description has no requirements, the graph skips straight to the report. If search or scoring is down, every row becomes Unverified and a warning is shown.

02

Code decides what's claimed

The model's answer is an opinion. Before anything is shown, every positive answer has to get through these checks.

1

Did the model cite a snippet that was retrieved for this requirement?

Not any snippet: one of the ones found for this exact requirement.

No → Unverified
2

Is its confidence at least 0.5?

Unsure answers are never rounded up to yes, and unsure "not met" answers aren't shown as gaps either.

No → Unverified
✓

Then the model's answer stands, with its citation

The citation is a permalink to the commit that was indexed, so it keeps pointing at the right lines.

Why not just ask a model "is this a fit?"

It would answer confidently, with no proof. Here a model can lean yes, but it can't create a claim by itself.

  • Text pasted into a job description can only change the list of requirements. A "Met" still has to cite a real snippet, and the snippet is shown so you can check it.
  • Near misses aren't matches. Docker isn't Kubernetes, JWT isn't OAuth2, LangGraph isn't LangChain.
  • An outage claims nothing. If a model is down, every row is Unverified and the score is 0.
03

Code is proof. The CV is a claim.

There are two kinds of evidence and they are never mixed: they are stored apart, searched apart, scored apart, and look different in the report.

In the report, GitHub evidence has a solid badge and CV claims have a dashed one. CV rows sit in their own dashed box, under a "Not proven by code" label. Code from a folder that isn't on GitHub yet is marked Code and has no link.

05

Synced with GitHub

The evidence is the candidate's public repositories. The server keeps its index in step with GitHub on its own, so a project pushed today can be cited today, with no redeploy.

  1. 1

    Check every 30 minutes

    The server asks GitHub for the latest commit of each public, non-fork repo. That's one small call per repo.

  2. 2

    Re-index only what changed

    A repo with a new commit is downloaded at that commit, split into line-ranged snippets, and embedded again. Unchanged repos cost nothing.

  3. 3

    Swap it in at once

    Checks keep running during a sync. Each repo's snippets are replaced in one step, so a check never sees half a repo.

  4. 4

    Drop what's gone

    A repo that is deleted or made private is removed at the next check. Secrets, .env files and build output are never indexed.

06

What it doesn't do

Knowing the limits is part of reading the report honestly.

It only sees public code

Work done at a job lives in private repos, so it can't be cited. That's what "Stated on CV" is for.

"Not met" means "not in these repos"

It's a statement about the evidence, not about the person. A gap is something to ask about in an interview.

Nothing you paste is stored

The job description is used for one check and thrown away. Your IP is kept only in memory for the hourly rate limit.

The model can still be wrong

The rules stop unproven claims, not every mistake. Every Met shows its snippet, so you can open it and judge for yourself.
